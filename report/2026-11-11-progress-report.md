## 2. 動機與決策

### 2.1 為什麼轉向 edge

上一期的數字讓我們重新檢視兩件事。

**(1) 在 edge 的 die 大小下，切 chiplet 省不到良率的錢。**

用 Chiplet Actuary 的參數（7nm 瑕疵密度 0.09/cm² N0043、cluster 參數 c=10 N0048、D2D 介面佔面積 10% N0051），比較「每顆良品要用掉多少矽面積」。正值表示切開反而更貴：

| 總面積（7nm） | 單顆良率 | 切成 2 塊 | 切成 4 塊 |
|---|---|---|---|
| 12.7 mm²（Expert Streaming 測試晶片的 die 大小） | 98.9% | +9.4% | +9.1% |
| 50 mm² | 95.6% | +7.8% | +6.5% |
| 100 mm² | 91.4% | +5.7% | +3.1% |
| 200 mm² | 83.7% | +1.6% | −3.3% |
| 400 mm² | 70.2% | −6.0% | −14.8% |
| 800 mm² | 49.9% | −19.1% | −33.2% |

> 計算方式：負二項良率模型 Y = (1 + A·D/c)^(−c)；只算矽面積，**沒算封裝成本與組裝良率**。算進去之後，切開會更不划算。

→ 損益平衡點大約在 150～200 mm²。edge 的 die 多半小於 100 mm²，所以 **edge 用 chiplet 的理由不是良率**，而是以下幾點：

- **重用**：同一顆 chiplet 用在不同產品，攤掉一次性設計成本。
- **可擴充**：同一顆 SoC 可以外掛不同數量的加速 chiplet。
- **異質製程**：運算用先進製程，其他部分用便宜製程。
- **記憶體放進封裝**：例如把 flash 做成 chiplet 放進封裝。

**(2) 限制 edge 的是記憶體，而這正是 Tack 的 KV 問題。** 見 §7.3、§7.5。

### 2.2 關鍵決策與理由

| 決策 | 理由 |
|---|---|
| 先做驗證器，再大量抽數字 | AI 抽錯數字時不會報錯；沒有驗證器，就不知道錯了多少 |
| 每篇抽兩次（A、B），一致才入庫 | 驗證器只能抓格式、單位、範圍錯誤，抓不到「數字對、條件錯」，例如 MAC 和 OPs 混用。兩次獨立抽取是「雙人輸入」的老方法 |
| 用 Claude Code 無頭模式抽取，不用 API | 這台機器沒有 SDK 和 API key；Claude Code 已登入。抽取時只開放 Read 權限，不能寫檔、不能上網 |
| 檢索包成 MCP 工具，不用向量資料庫 | DSE 要的是精確條件篩選（例如「LPDDR5X、實測、edge」），結構化表格比語意搜尋準。MCP 讓任何支援它的 harness 都能直接用 |
| 數字標 `value_kind` | 實測、規格目標、論文假設、廠商峰值，在 DSE 裡的分量不同，之前沒有欄位區分 |
| 查詢預設也回傳未複核的數字，但每筆都標示 | 目前 0 筆複核；預設只回已複核的話，agent 什麼都查不到。論文要用的數字，用 `mode=release` 只取已複核的 |
| schema 直接改版 | 指導者指示「直接照這個做」。**但 README 規則 4 要先跟學長確認，請學長補確認**（§12） |

## 5. 實驗二：兩次獨立抽取（A/B）

### 5.1 方法

- 同一篇論文開兩個 Claude Code session 抽取，彼此看不到對方的答案。模型是 Claude Opus 5.5，effort high。
- 抽取規則（`tools/extract_prompt.md`）：
  - 只抽文件自己的數字；引用別人的數字放進「線索」。
  - 引句要逐字複製，頁碼用 PDF 的頁數。
  - 換算單位時記下原值，並標明數字的性質。
- 比對：同參數、同單位、數值差 ≤ 0.5% 算一致；一致之後還要通過出處檢查和驗證器才入庫。

- 費用：抽取共 $14.5（Claude Code 計價的等值金額），平均每個入庫數字約 $0.05。每次抽取 39 秒～3.5 分鐘，三篇平行跑。

### 5.3 分析

- **抽兩次確實抓到了單次抽取會漏掉的錯。** NN-Baton 的 TOPS/W，A 算出 41.67，B 算出 83.3，剛好差 2 倍，就是「1 MAC = 2 OPs」的混用。schema 裡早就把這列為常見錯誤，但模型還是犯了；只抽一次的話，錯的那個會直接入庫。
- **論文越長、表格越多，一致率越低。** 9 頁的 Monad 是 94%；KVNAND 有 66～67 筆，只有 67%。不一致多半是「一方多抽了條件不同的同類數字」，不一定是錯，但需要人看。
- **兩次一致不代表一定對。** 兩次都是同一個模型，可能犯同樣的錯。所以一致只是「可以入庫」，不是「可以引用」，仍然要人工複核。
- **抽到的數字多半是假設值。** 全庫 373 個數字裡，論文假設 45%、實測 23%、推算 18%、廠商宣稱 10%、規格值 4%。DSE 用的時候要依性質加權。

## 6. 實驗三：agent 透過 MCP 查知識庫

### 6.1 方法

- 30 題標準題目（`eval/questions.yaml`），每題寫好「應該引用哪些 num_id」。
- 題型：查值 21、比較或計算 4、要提醒數字性質 2、知識庫沒有 2、前提有錯 1。
- 兩種測試：
  - **retrieval**：直接呼叫查詢函式，看該出現的 num_id 有沒有出現。用來測工具，免費、可重現。
  - **agent**：用 Claude Code 無頭模式，**只開放 chiplet-kb 的 MCP 工具**，不能讀檔、不能上網。問題原樣丟進去，看答案有沒有引用該引用的 num_id、有沒有提到該提的事。

### 6.2 結果

| 執行 | 知識庫數字數 | retrieval | agent | 平均輪數 | 費用 | 失敗原因 |
|---|---|---|---|---|---|---|
| 11/10 17:51 | 146 | 30/30 | 29/30 | — | $1.34 | Q22：agent 寫「對不上」，評分關鍵字漏了這個說法（評分的錯） |
| 11/10 17:53 | 146 | 30/30 | **30/30** | 4.1 | $1.11 | — |
| 11/10 18:24 | 373 | 30/30 | 29/30 | 4.0 | $1.14 | Q27：見下 |

### 6.3 分析

- **資料多了 2.5 倍，查詢沒有退步。** 數字從 146 增加到 373，retrieval 仍然是 30/30。
- **agent 不會編造。**
  - 問「LPDDR6 的 pin 速率」，它回答知識庫沒有，並指出只有一份候選文件。
  - 問「MI300X 用的 HBM4」，它指出前提錯了，MI300X 用的是 HBM3（N0012）。
- **agent 會主動提醒限制。**
  - Gaudi 3 的 SRAM 頻寬，它指出白皮書兩處寫法對不上，還自己發現 12.8 + 6.4 = 19.2，推測其中一個是讀寫合計，並標明這是推測。
  - 幾乎每題都會提醒「未複核，不能直接寫進論文」。
- **Q27 失敗：知識庫缺公式。** 題目要求用 Chiplet Actuary 的參數算 50 mm² 的良率。知識庫有參數（N0043、N0048），但沒有良率公式；評測指令又要求它「不要用自己的知識補」，所以它拒絕計算。agent 的行為是對的。
  - 這代表 **DSE 用得到的公式（良率、成本、roofline）也應該做成知識庫的內容**，不只存參數。

|---|---|---|---|---|---|---|
| BoW 2.0 | 規格 | ≤ 32 GT/s（N0021） | ≤ 0.5～1 pJ/bit（N0022、N0023） | ≤ 4 ns 無 FEC、≤ 15 ns 有 FEC（N0024、N0025） | — | 規格上限 |
| Simba GRS | Simba | 11～25 GT/s（N0036） | 0.82～1.75 pJ/bit（N0037、N0038） | 每 hop 20 ns（N0039） | 每顆 100 GB/s（N0040） | 實測 |
| UCIe（FSE-DP） | Expert Streaming | 4～24 GT/s（N0135、N0136） | — | **4.02 ns**（N0137） | 288 GB/s（N0134） | 實測 |
| GRS（評估設定） | NN-Baton | — | 1.17 pJ/bit（N0103） | — | — | 論文假設 |

- 2026 年的 UCIe 測試晶片，D2D 延遲是 4.02 ns。2019 年的 Simba 每經過一顆 chiplet 要 20 ns。兩者量的範圍不同（UCIe 只量介面兩端，Simba 是每 hop），但數量級的差距說明，**切 chiplet 的延遲代價已經小很多**。
- 同一篇 NN-Baton 裡，D2D 能耗出現 1.17（N0103）和 3.34 pJ/bit（N0104）兩個值。抽取時已在條件欄標註「可能含其他開銷，需人工確認」。

### 7.3 記憶體：edge 和資料中心差兩個數量級

| | 外部記憶體總頻寬 | 每 bit 能耗 |
|---|---|---|
| edge：LPDDR5X 8 channel（KVNAND Base-1） | 64 GB/s（N0346） | 7.0 pJ/bit（N0344） |
| edge：LPDDR4（Kelle） | 64 GB/s（N0319） | — |
| edge：DDR3-1600 ×4（Expert Streaming 評估設定） | 102.4 GB/s（N0141） | — |
| edge：NAND flash 8 channel（KVNAND） | 38.4 GB/s（N0353） | 4.9 pJ/bit I/O（N0348） |
| 對照：MI300X HBM3 | 5300 GB/s（N0016） | — |
| D2D（對照用） | — | 0.5～1.75 pJ/bit（§7.2） |

- **edge 的記憶體頻寬是 MI300X 的 1/50～1/140。**
- **跨一次 die 比讀一次 LPDDR5X 省電約 4～14 倍**（7.0 ÷ 1.75 到 7.0 ÷ 0.5）。所以如果切 chiplet 能讓片上 SRAM 總量變大，把權重或 KV 留在片上，多出來的跨 die 流量是划算的。Expert Streaming 把所有 chiplet 的 SRAM 當成一個共用池（每顆 14～16 MB，N0144、N0145），就是這個思路。

### 7.4 切分：最佳切分數取決於總規模

| 來源 | 條件 | 最佳切分 |
|---|---|---|
| NN-Baton | 總 2048 MAC、每顆 chiplet ≤ 2 mm² | 4 顆（N0088） |
| NN-Baton | 總 4096 MAC、每顆 chiplet ≤ 3 mm² | 2 顆（N0089） |
| KVNAND | LLaMA3.1-8B、context 1K，16 顆 flash 運算 die | KV 專用 die 1 顆（N0340） |
| KVNAND | LLaMA3.1-70B、context 100K，8 顆 flash 運算 die | KV 專用 die 4 顆（N0341） |
| Monad | 3 顆 chiplet 成本研究 | 被動中介層佔成本 > 15%、主動中介層 > 30%（N0117、N0118） |

→ 最佳切分數會跟著總規模、面積上限、模型大小、context 長度改變。KVNAND 的例子裡，context 越長，分給 KV 的 die 越多。**沒有一個固定的「最佳切法」**，這正是需要 DSE 的理由。Monad 的數字也說明，**在 edge 選封裝本身就是主要成本**，和 §2.1 的結論一致。

### 7.5 KV 大小和 edge 記憶體容量

**不同模型每 token 的 KV 大小，相差約 30 倍：**

| 模型 | 每 token KV | 來源 |
|---|---|---|
| Mistral-7B，INT8 | 0.066 MB | N0259（CacheGen） |
| Llama-3-8B，FP16，GQA（8 KV head） | 0.131 MB | 用架構算（32 層 × 8 head × 128 維 × 2 × 2 B） |
| Llama-34B | 0.237 MB | N0261（CacheGen） |
| LLaMA2-7B，FP16，MHA | 0.500 MB | N0321（Kelle） |
| OPT-13B，FP16 | 0.800 MB | N0147（vLLM） |
| OPT-66B，FP16，MHA | 2.207 MB | N0184（DistServe） |

**學弟 A 的 17 個 agent trace**（Claude Code 14 個、Codex 3 個）每個 session 的最大 context：

| | 中位數 | 90 百分位 | 最大 |
|---|---|---|---|
| context 長度 | 124,824 | 302,931 | 546,634 token |
| KV：Llama-3-8B FP16 | **16.4 GB** | 39.7 GB | 71.6 GB |
| KV：Mistral-7B INT8 | 8.2 GB | 20.0 GB | 36.1 GB |
| KV：LLaMA2-7B FP16（MHA） | 62.4 GB | 151.5 GB | 273.3 GB |

**edge 裝置的記憶體容量**：手機 DRAM 8～16 GB（N0360、N0361），筆電 < 64 GB（N0362）。Kelle 和 KVNAND 的評估平台都是 16 GB（N0318、N0345）。

→ **一半的 agent session，光 KV 就超過手機 DRAM 的上限**，這還沒算模型權重。要讓 agent 在 edge 上跑，KV 的量化、逐出、卸載不是選配，而是必要的。

> 假設：一個 session、batch 1、KV 不壓縮。trace 是我們自己的開發 session，樣本少，而且偏向長任務。

### 7.6 decode 速度的上限（用知識庫的數字直接算）

decode 時每生成一個 token，要把權重和所有 KV 從記憶體讀一遍，所以速度上限 ≈ 記憶體頻寬 ÷（權重 + KV）。代入 Kelle 的設定：

- LLaMA2-7B INT8 權重 6.5 GB（N0322）
- 每 token KV 0.5 MB（N0321）
- 頻寬 64 GB/s（N0319）
- 容量 16 GB（N0318）

| context | KV 大小 | 放得下 16 GB？ | decode 上限 | KV 存成 2-bit（理想值） | decode 上限 |
|---|---|---|---|---|---|
| 1K | 0.5 GB | ✅ | 9.1 tokens/s | 0.1 GB | 9.8 tokens/s |
| 8K | 4.1 GB | ✅ | 6.0 | 0.5 GB | 9.1 |
| 16K | 8.2 GB | ✅ | 4.4 | 1.0 GB | 8.5 |
| 32K | 16.4 GB | ❌ | （2.8） | 2.0 GB | 7.5 |
| 125K（agent 中位數） | 62.4 GB | ❌ | （0.9） | 7.8 GB | 4.5 |

- context 一長，KV 就取代權重，成為記憶體流量的大宗。在 125K 時，KV 是權重的將近 10 倍。
- 把 KV 存成 2-bit，125K 的 agent session 就能放進 16 GB，速度上限也從 0.9 提高到 4.5 tokens/s。

> 這是上限估算，不是模擬：沒算運算時間、沒算 KIVI 保留的全精度 token 與量化參數，2-bit 只取理想的 8 倍壓縮。用意是示範「**知識庫的數字可以直接接到 DSE 的效能模型**」。

### 7.7 同一顆硬體，換 KV 策略的效果

| 方法 | 硬體與模型 | 用 KV 策略 | 不用（基準） | 倍數 |
|---|---|---|---|---|
| H2O（只留 20% KV） | T4 16GB，OPT-6.7B，512+32 token | 35.1 tokens/s（N0211） | 20.2（N0217） | 1.7× |
| H2O | T4 16GB，OPT-30B，512+32 token | 12.7（N0212） | 8.1（N0218） | 1.6× |
| ShadowKV | A100，Llama-3-8B-1M，60K context | 455.1（N0278） | 160.6（N0287） | 2.8× |
| ShadowKV | A100，Llama-3-8B-1M，122K context | 239.5（N0279） | 80.8（N0288） | 3.0× |

→ **硬體完全不變，只換 KV 策略，吞吐就差 1.6～3 倍。** 所以挑硬體時一定要把 KV 策略一起考慮，這就是 Tack「KV 策略與硬體共同設計」的實證。

這些實驗都跑在 GPU 上，搬到 edge 的效果還需要模擬確認。

### 7.8 學弟 A 的 trace 特徵

| 特徵 | 數值 |
|---|---|
| session 數 | 17（Claude Code 14、Codex 3；排除 2 個 fork） |
| 每個 session 的 LLM 呼叫數 | 平均 73、中位數 64 |
| 快取命中（cache_read ÷ context） | 中位數 95%、p10 83% |
| 觸發 context 壓縮的 session | 2/17 |

由下而上看，**能把 session 分成兩群的特徵**（在 20%～80% 的 session 出現）有三個：長 context（最大 > 10 萬 token，53%）、長任務（> 50 步，53%）、tool 時間 > 30%（24%）。這三個可以當成 workload 標籤或 DSE 維度的候選。

- **快取命中高達 95%**：agent 的前文大多可以重用，KV 重用（prefix caching）對 agent workload 特別重要。

## 9. 從這些實驗學到什麼

### 知識

| 知識 | 依據 |
|---|---|
| edge 的 die 小於約 150 mm² 時，切 chiplet 沒有良率好處 | §2.1 |
| edge 的記憶體頻寬是資料中心的 1/50～1/140 | §7.3 |
| 跨 die 搬資料比讀 LPDDR5X 省電 4～14 倍 | §7.3 |
| UCIe 測試晶片的 D2D 延遲約 4 ns | §7.2（N0137） |
| 每 token KV 隨模型架構與精度相差約 30 倍 | §7.5 |
| 一半的 agent session，KV 就超過手機 DRAM | §7.5 |
| 同一顆硬體換 KV 策略，吞吐差 1.6～3 倍 | §7.7 |
| agent 前文的快取命中約 95% | §7.8 |

### 架構

- **edge chiplet 常見三種切法**：
  - 同構運算 chiplet 加共用 SRAM 池（Expert Streaming、Simba、NN-Baton）
  - NPU 加記憶體或 flash chiplet（Cambricon-LLM、KVNAND）
  - host SoC 外掛加速 chiplet（Renesas R-Car X5H，候選文件）
- **edge 的記憶體階層**：片上 SRAM／eDRAM → LPDDR（封裝內或板上）→ NAND flash。HBM 不在選項裡。

- **edge 還缺匯流排寬度 `mem_bus_width`**；每 mm 邊長的 D2D 頻寬也只有通用來源。
